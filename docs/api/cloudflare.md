# Cloudflare access and publishing API

[API index](README.md)

The optional Cloudflare entrypoint serves the existing desktop through a Cloudflare Tunnel and Access application. [Startup](../startup.md#cloudflare-access) owns configuration and deployment. The [`cloudflare`](../../apps/server/internal/cloudflare) package owns JWT verification, the dedicated desktop loopback listener and connection lifetime. The separate [`cloudflareapi`](../../apps/server/internal/cloudflareapi) client supplies account checks and resource operations, while [`cloudflarepublish`](../../apps/server/internal/cloudflarepublish) owns explicitly published VM project services on another listener. Tailscale remains an independent private desktop entrypoint; transports do not change execution targets.

## Authentication and authorization

Every request, including UI assets and document reads, must contain one `Cf-Access-Jwt-Assertion` application token. AXV verifies its RS256 signature with the configured team's HTTPS signing keys, exact issuer, single application audience, validity timestamps, `type: app` and the explicitly configured owner's stable `sub`. Service tokens and other owners are rejected. Email addresses, cookies alone, forwarded headers and the connector's loopback address do not establish authority. AXV never binds the first visitor as owner.

Signing-key retrieval uses a bounded HTTPS client without environment proxies or redirects. Keys are cached and refreshed on rotation, with a five-second fetch window and failure backoff to bound unknown-key requests. Cached valid keys can continue verifying unexpired JWTs while a refresh is unavailable. JWTs and identity claims are not returned in status or logged. Desktop access needs no Cloudflare API credential; optional account management stores its API token in the private profile and never returns it to a browser. Tunnel connector credentials remain external. After verification, Access identity headers and authentication cookies are stripped before dispatch to feature handlers, keeping bearer tokens out of compute forwarding.

The listener accepts only actual loopback peers and the configured public HTTPS Host. Supplied Origin must exactly match on reads; mutations and WebSocket upgrades require the exact HTTPS Origin. Its trusted context authorizes shared feature guards without rewriting Host, Origin, RemoteAddr or TLS state. The local-only primitive continues to reject these requests. The ordinary local desktop listener also requires a real loopback peer and loopback Host, including for document reads.

Both remote transports use the same explicit [route policy](../../apps/server/internal/server/remote.go). Remote configuration/status, VM preparation and application installation/administration remain local-only. Launcher identity, private host routes and unknown API families are excluded. Project previews remain local-only; a tunnel does not grant preview browsing or host-network access.

## Connection lifetime

An accepted owner JWT must have a signed lifetime `exp - iat` of at most **15 minutes**. Longer tokens are rejected even if only seconds remain. Every HTTP request, SSE response and WebSocket ends at its original signed expiry; AXV cancels the request and closes its actual connection, including upgraded streams. Reconnecting with the same token never extends that deadline. Configure both the Access application and its matching Allow policies for a session of at most 15 minutes. A new token requires Cloudflare's policy evaluation; [its session documentation](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/) describes how the global session and application token differ.

This is the explicitly accepted [finite-lease product contract](../product.md#cloudflare-service-isolation-and-authorization). Offline signature validation does **not** provide continuous policy freshness or immediate detection of a provider-side logout, policy change or token revocation. Existing verified connections can last only until the original expiry. During a signing-key/control-plane outage, already cached valid keys may verify an unexpired short token, while unknown keys and expired or overlong tokens fail closed. No outage fallback or new connection renews an old lease. Disabling the desktop entrypoint or unpublishing a service closes its active connections locally; Cloudflare's own edge checks still apply to new requests.

Disconnection ends an ordinary Host Terminal shell and detaches Codex views; independent Codex runs, VMs, guest terminals and accepted tasks retain their feature-owned lifetimes. Local clients and Tailscale clients remain independent. Reconnecting never substitutes another conversation or run. Cloudflare edge restarts can also interrupt WebSockets; see [Cloudflare's WebSocket guidance](https://developers.cloudflare.com/network/websockets/).

Shared dashboard JSON requests identify themselves as AJAX so Access can return `401` instead of a login redirect, following [Cloudflare's session guidance](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/#ajax). Authorization failures remain visible without reloading the desktop or replaying writes; keep drafts open and sign in again in another tab before retrying.

## Local status and control

`GET /api/cloudflare/status` requires the raw loopback peer/Host/Origin checks and returns:

```json
{
  "instanceId": "desktop-...",
  "enabled": true,
  "configured": true,
  "state": "listening",
  "url": "https://axv.example.com",
  "listen": "127.0.0.1:3002"
}
```

States are `disabled`, `starting`, `listening`, `error` and `stopped`. `listening` proves only that AXV's local authenticated entrypoint is bound. It does not verify cloudflared, DNS, Access policy, public reachability or WAF configuration. `configured` describes validated, complete profile settings; the panel can label incomplete setup as **Setup required** without introducing another API state. `listen` may identify the configured origin address while the entrypoint is disabled and does not itself prove a bound listener. A local `error` explains configuration, listener or lifecycle failures; identity settings and JWTs are omitted. `axv cloudflare status [--json]` verifies the active desktop instance before displaying status, without initializing a profile or starting a connector.

`PUT /api/cloudflare` requires the raw local checks and exact local Origin. The body contains only `{ "enabled": true }` or `{ "enabled": false }`. The controller serializes changes, holds the shared profile lock and persists only `cloudflare.enabled`, preserving other configuration. Failed persistence leaves live connections unchanged. Once saved, the transition completes independently of a disconnected browser. Explicit enable retries an errored/stopped entrypoint with current configuration; changing other settings requires disable followed by enable. A failed close prevents overlapping starts and remains visible until desktop restart.

Missing/null/non-boolean values, unknown fields, trailing JSON and bodies over 4096 bytes return `400 invalid_cloudflare_request`. Untrusted status/control requests return `403 cloudflare_local_only`. A busy profile lock returns `409 cloudflare_config_busy`; invalid configuration or failed persistence returns `500 cloudflare_config_failed`. A failed previous close returns `409 cloudflare_close_failed`, and shutdown returns `503 cloudflare_stopping`. Successful control returns the safe summary below. After an interrupted response, inspect status before explicitly retrying.

The tunnel entrypoint returns `401 cloudflare_unauthorized` for missing or invalid Access credentials, `403 cloudflare_forbidden` for an invalid peer/Host/Origin, `403 remote_local_only` for local-only routes and `404 not_found` for excluded routes. Failures use the shared `{ error, code }` JSON shape and never include token claims or signing-library errors.

`GET /api/connection` includes a safe `cloudflare` summary with `enabled`, `configured`, `state`, an optional HTTPS `url` and a fixed `message`. It excludes the local listener and raw diagnostics. Remote viewers can inspect this summary but cannot configure either desktop transport. Status/control responses use `Cache-Control: no-store`. The Cloudflare panel polls only while active; failure marks retained information as stale and hides a current-looking address. Details are fetched only when the separate Diagnostics section is open in a local active view. Setup reads and edits configuration only from the local desktop; public Help remains available remotely.

Normal desktop shutdown closes this entrypoint without changing its saved preference. AXV does not create or supervise cloudflared, Access applications, the system Tailscale service or firewall. Account-managed publishing changes only its own reviewed DNS and ingress resources, as described below.

## Configuration and account checks

| Method | Route | Authority and result |
| --- | --- | --- |
| GET | `/api/cloudflare/capabilities` | Local or authenticated desktop owner; `{configure,publish,traffic,health}`. Only local callers receive `configure:true` |
| GET | `/api/cloudflare/config` | Local only; `{instanceId,revision,access,account}` with `hasToken`, never the token |
| PUT | `/api/cloudflare/config` | Exact local Origin; reviewed complete configuration with original instance and revision |
| PUT | `/api/cloudflare/token` | Exact local Origin; rotate only the API token, preserving active access and publication identities |
| POST | `/api/cloudflare/wizard` | Exact local Origin; validate a setup step or list existing resources without changing Cloudflare |
| GET | `/api/cloudflare/health` | Local or authenticated desktop owner; token, DNS read access and tunnel status, cached for one minute |
| GET | `/api/cloudflare/traffic?hours=24` | Local or authenticated desktop owner; real zone traffic or an explicit unsupported reason |

Configuration uses camelCase HTTP fields. `access` contains `enabled` on reads and `listen`, `origin`, `issuer`, `audience`, `ownerSubject`; `account` contains `configured`, `hasToken` on reads and `accountId`, `zoneId`, `tunnelId`, `domain`, `listen`, `audience`. A configuration write contains `{instanceId,expectedRevision,access,account,tokenAction,token?}`; omit the read-only fields. `tokenAction` is `keep`, `replace` or `clear`; only `replace` accepts a nonempty token. Writes require the desktop entrypoint to be completely disabled and all service publications removed, including pending cleanup. Unknown profile fields and unrelated owners are preserved. Stale revisions or instances return `409`; failed or uncertain saves require inspection before retrying. Token rotation accepts `{instanceId,expectedRevision,token}`, checks the new credential against the current account resources, then updates only that credential under the profile lock. Rotation does not require disabling desktop access or removing publications.

Wizard input is `{step,token?,accountId?,zoneId?,tunnelId?,domain?,access?}`. Steps are `access`, `token`, `account`, `zone`, `tunnel`, `domain`. Omitting `token` reuses the saved credential. Account and zone selections are scoped, and publishing requires an existing remotely managed tunnel. Token validation checks activity; a DNS read check does not establish DNS Edit permission. Access validation checks configuration syntax, not an externally deployed policy or successful owner login. Inputs are bounded Unicode JSON objects, reject unknown fields and require `application/json`.

Health returns `{state,checkedAt,message,tunnelName?,tunnelStatus?}` with `unconfigured`, `healthy`, `degraded` or `error`. `?force=true` bypasses its cache. Neither `healthy` nor the desktop's `listening` proves public URL reachability. Traffic windows are 1, 6, 12, 24, 168 or 720 complete hours, subject to provider plan and permissions; the current partial hour is excluded so bucket alignment does not exceed the requested interval. Successful traffic includes `supported:true`, actual `since`/`until`, zone-wide `requests`, `bytes`, `cachedRequests` and hourly `series`. It is not per-tunnel or per-application traffic; provider failures and unavailable datasets never become fabricated zero counts. See Cloudflare's [GraphQL datasets](https://developers.cloudflare.com/analytics/graphql-api/features/data-sets/) and [limits](https://developers.cloudflare.com/analytics/graphql-api/limits/).

The API client confines requests to the official HTTPS endpoint, does not use environment proxies or redirects, and bounds time, pagination and complete response sizes. Errors omit provider response text and credentials. Read checks do not mutate cloud resources or install connectors.

## Published project services

Published services are independent of local preview registrations. Their durable journal captures the exact project binding, private host socket/configuration identity, port, generated hostname, cookie site, visibility and resource receipts. Application content never shares the desktop origin or handler. Local previews retain their independent access and stop behavior; [their contract](project-previews.md) owns that separate lifecycle.

### Browser isolation and hostname lifetime

`management.domain` is an allocation suffix. It must be an exact registrable domain or an existing public suffix recognized by the pinned Public Suffix List, including PRIVATE rules. An ordinary subdomain such as `apps.example.com` is rejected as an allocation suffix. The browser cookie site of every publication must differ from the desktop and all historical publications. A dedicated registrable domain, for example `example.net` while the desktop is on `example.com`, can therefore serve only one publication during that domain's AXV lifetime. Multiple publications under one suffix require actual public-suffix isolation; different ordinary subdomains alone are insufficient. The administrator must keep the dedicated site exclusive across profiles and external applications as well.

Clients submit a canonical **name** of 1–24 lowercase ASCII letters, digits or interior hyphens; the `xn--` IDNA prefix is reserved. AXV adds a cryptographically random 128-bit generation and allocates `<name>-<32-lowercase-hex-generation>.<domain>`. The generated label is one DNS level, and the exact address is returned with the accepted receipt. The submitted `domain` must equal the reviewed allocation suffix and current configuration before acceptance; a configuration change cannot silently publish to another domain. A name hint is not an alias and cannot select an old hostname. The original request ID always returns the same generation, hostname and binding. DNS or ingress belonging to another owner remains a conflict.

All historical cookie sites and hostnames remain reserved after Unpublish. Removed records are retained, and capacity limits never evict them to permit reuse. A new request cannot give an old site, hostname or browser storage to another project, VM, port or boot. This also applies when configuring a desktop origin: a site previously used by a publication cannot become the desktop site. Deleting an AXV profile does not clear browser state; do not reuse its sites for a different application.

Before serving guest code to a browser, the publication checks host-only cookie support and rejection of cookies at its actual public suffix and parent suffixes. An AXV-owned bootstrap and host/generation-bound proof perform this compatibility check. Failed checks stop at an explicit error, without clearing application state or treating the check as authentication. Browser background requests and WebSockets require a valid proof. The server's PSL alone is not a claim about every deployed browser's PSL version.

The reserved `/__axv/isolation` namespace never reaches the guest. A top-level browser navigation receives a nonce-protected check page; exact-origin JSON confirmation consumes a host/generation-bound 60-second challenge and sets a secure, HttpOnly, host-only compatibility proof for 15 minutes. The proof is not authentication and cannot extend the Access lease. It is invalid after a server restart or on another hostname/generation. Any Fetch Metadata headers classify a request as a browser, regardless of its User-Agent. Missing/incomplete metadata and unsupported browsers fail closed. Native clients without Fetch Metadata may use a versioned `Go-http-client`, `curl` or `axv` User-Agent; a request with no User-Agent is accepted only for GET/HEAD without Origin or Upgrade. These clients still require the existing identity, Host and mutation/WebSocket Origin checks. AXV's proof/challenge cookies never reach the guest.

Scripts, ordinary application sessions, localStorage, IndexedDB, dedicated workers, HTTP, SSE and WebSockets retain their own origin. Service worker registration/update is rejected so an application cannot persist an offline interceptor ahead of later AXV checks. Service-worker/offline PWAs are outside the supported application model. Withdrawal closes network reachability; it does not erase already delivered content or browser storage. Application responses force `no-store` for browser and Cloudflare/CDN caches, including streaming and upgrade responses; guest headers cannot override it. Proxied HTTP `Set-Cookie` headers are rewritten host-only; JavaScript cookies remain bounded by the exclusive cookie site and browser PSL. Access/AXV infrastructure credentials are stripped, and application `Authorization` remains separate from transport credentials.

| Method | Route | Result |
| --- | --- | --- |
| GET | `/api/cloudflare-publications` | `{instanceId,supported,reason?,domain?,isolation?,publications}` with retained original receipts |
| POST | `/api/cloudflare-publications` | Accept `{instanceId,requestId,binding,port,name,domain,visibility}`; `202` returns the original publication with `name`, `generation`, `domain` and generated `hostname` |
| POST | `/api/cloudflare-publications/:id/unpublish` | Accept `{}`; revoke the exact publication, then clean its cloud resources |
| POST | `/api/cloudflare-publications/:id/retry` | Accept `{}`; retry the original publication or its pending cleanup |

Controls accept the local desktop or an authenticated desktop owner. Mutations require the exact desktop Origin and `X-AXV-Host-ID` matching the captured binding; readers cannot manufacture authority with headers. Mutation bodies require `application/json`, one valid Unicode JSON object of at most 16 KiB, no unknown fields and no trailing JSON. These routes do not accept query parameters. Incomplete management settings or an already reserved dedicated site return `supported:false` with a specific reason; retained publications and their cleanup/resume controls remain available. `domain` and `isolation` describe the allocation suffix and mode (`dedicated-site` or `public-suffix`), `maxOwnerSessionSeconds:900`, unique hostnames and nonreusable retired sites. Ports are 1024–65535. The project must support private preview forwarding. New registrations capture the environment explicitly; retries never select a new VM, host or boot. Identical request receipts are recoverable after restart, while another payload with the same request ID returns a conflict. Limits are 64 nonremoved publications and 4096 retained receipts; capacity errors preserve existing identities.

`visibility` defaults to `owner`. Owner access verifies the configured issuer, publication application audience and stable owner subject on every request, independently of any edge policy. Configure the corresponding Access application externally to make browser authentication available. `public` is an explicit choice permitting Internet visitors without AXV owner authentication. Both modes accept only actual loopback peers and the exact publication Host. Supplied Origin must match its HTTPS origin on reads; mutations and WebSocket upgrades require that Origin. Both modes strip Access credentials before forwarding, preserve application HTTP/WebSocket paths, rewrite proxied `Set-Cookie` headers host-only and enforce separate origins. Withdrawal cancels and closes active HTTP/WebSocket connections; independent VM services, tasks and runs continue.

Publication states are `provisioning`, `published`, `unavailable`, `removing`, `removed` and `error`, with a specific `phase`, optional error and `cleanupPending`. Only `published` includes a URL; it reports a verified original target and configured DNS/ingress, not a successful public browser check. Closing a panel does not unpublish. Desktop shutdown closes the origin listener. Startup keeps retained routes **closed**, with `unavailable` / `restart-required`, until the owner reviews **Resume** and retries the exact original publication. It never silently selects another environment or creates a fresh publication; recorded removal cleanup may continue without reopening access. The dashboard confirms every non-cleanup retry that can reopen access, even when it retains an older status while refreshing. Cleanup retry is separate: recorded removal is irreversible for that publication and cannot become a resume.

Unpublish closes local reachability and active HTTP/SSE/WebSocket connections before persisting removal or cleaning cloud resources. A failed binding check withdraws its exact runtime before exposing a retryable state; Retry waits for that runtime's connections and target to finish closing before starting a replacement. Late health results cannot withdraw a replacement. If recording removal fails, access stays closed in that process, the original journal is preserved and the persistence failure remains visible. A queued worker cannot reopen the withdrawn route. On restart, an older journal still cannot reopen automatically. Repair storage and inspect the original receipts before retrying Unpublish; explicitly resuming means reopening that original application. The unreleased journal baseline is version **2**, with generation and cookie-site validation. Older, malformed or unknown journals are preserved and rejected, never silently migrated or reset.

Publishing creates a proxied CNAME and one exact hostname ingress rule on the selected existing tunnel. A random durable AXV ownership marker identifies its DNS records; prepared intents and returned receipts recover uncertain writes. A definitely unwritten fresh DNS/ingress attempt drops its prepared ownership, so later matching foreign resources cannot be adopted or deleted; a prior uncertain attempt retains its original proof. Existing foreign DNS or matching ingress rules cause conflicts rather than being adopted. Cleanup verifies ownership before deleting and preserves unrelated records, rules and opaque tunnel configuration fields. Cloudflare ingress updates have no cross-client compare-and-swap guarantee: AXV serializes its writes, checks snapshots and verifies the result, but external simultaneous edits can still race. Inspect conflicts and finish cleanup before changing the account or routing configuration; API token rotation remains available.
