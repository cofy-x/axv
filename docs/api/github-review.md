# GitHub Review API and ownership

The [GitHub Review application](../usage.md#github-review) uses the ordinary loopback desktop listener. Reads require a local peer and Host. Mutations also require the exact desktop Origin. AXV's authenticated remote listeners exclude this API family. The [GitHub Review service](../../apps/server/internal/githubreview) owns configuration, account binding, the review queue, commit evidence and local candidate comments.

| Method and path | Request |
| --- | --- |
| GET `/api/github-review` | Read settings, connection state and recent jobs. Use `?summary=1` to omit job bodies and read `hasJobs` for the attached `reviewAccount`. |
| GET `/api/github-review/inbox` | Read a page of `view=action`, `view=active` or `view=history`. Send the previous response's `nextCursor` to continue. |
| GET `/api/github-review/job` | Read one exact stored review by `repository`, `number`, `baseSha` and `headSha`, including its candidate and evidence details. |
| GET `/api/github-review/vm-readiness` | Check the VM and project selected for `repository`. Reports `status` and a remediation `message`. Checks the registered Compute host, running guest, Project Tasks capability, VM allocation and exact project binding. No test is submitted. |
| PUT `/api/github-review/config` | Save `repositories`, `repositoryPolicies`, `publishRepositories`, `intervalMinutes`, `dailyLimit`, `enabled`, optional `watchOnly` and the previously read `revision`. |
| POST `/api/github-review/connect/{github\|codex}` | Attach the host CLI login or start a provider device-code login. |
| POST `/api/github-review/disconnect/{github\|codex}` | Detach the integration and cancel any pending login. |
| POST `/api/github-review/candidate-comparison` | Queue an operator-confirmed assertion on the common ancestor and PR head for one candidate. Replaying the same request reuses the original run. |
| GET `/api/github-review/candidate-comparison/{id}` | Read the saved runtime, assertion and both VM receipts for one comparison owned by the connected GitHub account. |
| POST `/api/github-review/approve-comparison-scenario` | Approve a previously confirmed assertion as a reusable scenario for its repository. |
| POST `/api/github-review/candidate-followup` | Open a local follow-up for a historical issue on the current reviewed comparison. |
| POST `/api/github-review/candidate` | Save a local disposition, note, evidence references and optionally link a finding on an earlier version. |
| POST `/api/github-review/candidate-draft` | Create or update a local Markdown comment for a finding on the current reviewed diff. |
| POST `/api/github-review/candidate-draft-reviewed` | Mark the exact saved local draft as reviewed or return it to the inbox. |
| POST `/api/github-review/run` | Wake the enabled worker for an immediate scan. Both connections are required. |
| POST `/api/github-review/review-latest` | Check one displayed PR against live GitHub using its `repository`, `number`, `baseSha`, `headSha` and configuration `revision`. Queue its current eligible comparison for local review, including while polling is paused. A completed comparison is reused. Full daily budgets defer work until reset. |
| POST `/api/github-review/review-pr` | Look up one open, ready PR using `repository`, `number` and configuration `revision`. The repository must be watched or GitHub must currently request a review from the connected account. Prior discovery is optional. This local review takes priority over automatic analysis, shares the daily Codex limit and works while polling is paused. The snapshot also contains `selectedReview` with the exact stored `repository`, `number`, `baseSha`, `headSha` and `status`. A completed comparison is reused. |
| POST `/api/github-review/retry` | Retry analysis for a failed or stale job, or attach evidence to an eligible legacy review, using its `repository`, `number`, `baseSha`, `headSha` and the previously read configuration `revision`. Polling and both connections are required. |
| POST `/api/github-review/refresh-checks` | Refresh upstream evidence for a captured PR using `repository`, `number`, `baseSha`, `headSha` and the current configuration `revision`. Works while polling is paused. |
| POST `/api/github-review/retry-test` | Choose a quick test for one reviewed comparison using `repository`, `number`, `baseSha`, `headSha`, `revision` and the latest finished `attempt` number (zero before the first attempt). Omit `testId` for automatic selection or send a saved profile ID for a one-time override. Works with polling paused. |
| POST `/api/github-review/confirm-test-recommendation` | Queue one recommended quick test using `repository`, `number`, `baseSha`, `headSha`, the current configuration `revision` and the snapshot's `recommendationId`. Works with polling paused. |

Successful settings and worker operations return the current snapshot with `config`, `github`, `codex`, `jobs`, `budget` and, after scanning, `lastPollAt`. `budget` contains `used` and `resetsAt`. Connection state can include an in-memory device login attempt. An active attempt exposes the official verification URL and one-time code. Credentials remain with the local CLIs. Refresh the snapshot after a revision conflict or an uncertain response. The connected owner can see local candidate comments and historical comment links on the local listener.

The inbox returns `{account,jobs,nextCursor?}` with up to 25 rows. Each row has an `inboxGroup` of `action`, `active`, `recent` or `earlier` for the requested view and omits detailed logs and candidate history. Views are scoped to the attached account. A PR can appear in both the action and active views. The server filters across all stored rows, ordered by insertion, with a bounded scan per request. Continue with the opaque cursor even on a sparse page. The exact job lookup returns `{account,job}` and returns 404 if the requested commit pair is unavailable. Use that lookup to refresh an open detail independently of inbox pagination.

The `discovery` observation reports whether a GitHub scan is in progress, the next interval deadline while scheduled discovery and both connections are active, and the latest successful scan's start time. A missing `nextScanAt` with an enabled schedule and available connections means the worker is due to scan. Each scan also updates `lastPollAt`, including failed attempts. A failed scan exposes `discovery.error` and retains `discovery.lastSuccessAt`. The Codex review budget limits analysis starts independently of discovery.

`watchOnly: true` limits automatic discovery and queued review starts to watched repositories. The default includes direct review requests. Turning this on holds outside-repository requests that are already queued. These remain in the inbox with a hold reason, and the reviewer can explicitly review one using **Review latest commit** while the request is still valid.

The worker polls open ready PRs in up to 100 configured GitHub.com repositories and direct review requests for the connected user. It captures the canonical repository, PR number and base/head SHA. It validates the direct request against current PR metadata. Job identity includes the GitHub login, repository, PR number and head SHA. A repeated head preserves completed work, and discovery of a newer head marks earlier rows stale, including completed reviews and their evidence. Configuration and jobs live under the desktop data directory in `github-review/reviews.sqlite`. Use a separate `AXV_HOME` when moving from an experimental GitHub Review build to the public database baseline. AXV preserves incompatible databases and reports that GitHub Review is unavailable for that profile. Login attempts and the latest polling observation are process-local. A stopped desktop interrupts active analysis. The next desktop launch can resume the queue.

After a base tip changes with the same PR head, AXV compares the original and observed merge bases. An equivalent three-dot diff keeps its recorded review against the original commits. A changed or unverifiable comparison marks the review stale and exposes the observed base. Verified equivalence on a later poll can restore a completed review. A new analysis records its own comparison and local candidate decisions. [GitHub compare API](https://docs.github.com/en/rest/commits/commits#compare-two-commits)

Before starting analysis, the worker verifies the selected PR and captures its title and description from the same GitHub response. New reviews expose these fields in `evidence.review.authorContext`. The title is limited to 1 KiB and the description to 8 KiB at UTF-8 character boundaries. An empty description is valid. The corresponding `titleTruncated` or `descriptionTruncated` flag records a cut. Later edits to the PR text keep the original review snapshot and consume no additional review start by themselves.

The worker fetches Git objects using the captured SHAs, computes the merge-base diff, and supplies the patch, bounded related text and captured author context to the official non-interactive Codex CLI. It treats the PR text as an untrusted account of the author's intent. The review compares it with code, tests and documented behavior when identifying unintended regressions. The patch limit is 192 KiB and the merge-base search budget is 1,024 commits. Oversize changes or unreadable revisions become visible errors. The model receives no GitHub credential, and its shell and optional external tools are disabled. Proposed finding locations must match a changed line in the supplied diff.

`dailyLimit` accepts 1 to 1,000 review starts per local calendar day on the AXV host and defaults to 10. AXV reserves a slot in the same transaction that starts a review. The count persists across restarts and GitHub account changes within the same AXV data directory. Queued analysis waits when the limit is reached. Retrying a VM test preserves the count and the candidate comments.

`repositoryPolicies` maps a watched repository to `{rules, testCommand, testProfiles, comparisonRuntimes}`. Names match the watch list case-insensitively. Rules accept up to 4,096 UTF-8 bytes. A test command takes up to 32 nonempty arguments of at most 512 bytes each. With no profiles, AXV runs the existing `testCommand`. An empty command and no profiles disable the quick test. `publishRepositories` must be an empty array. All new candidates remain local. Existing published comment links remain available in history.

A policy can define up to eight ordered `testProfiles`. Each has a unique stable `id`, display `name`, required repository-relative `entryPath`, `command` argument array and optional `appliesTo` list of up to 16 repository-relative file or directory paths. Directory matches respect path components. An empty scope matches any change. When profiles are present, the first profile with a matching scope and a regular entry file at the captured head supplies the command. Use the last profile for an explicit fallback. A direct review request outside the watched list has no local quick-test policy.

Scoped selection compares the captured base and head with GitHub's three-dot comparison, including deleted paths and both sides of renames. At GitHub's 300-file limit AXV verifies the complete list with Git. An unverified comparison or tree is an error. If all verified profiles are out of scope or their entry files are absent, the attempt ends as `not_applicable` before creating a VM task. A legacy command invoking a recognizable repository script also checks that entry. Other legacy commands run as configured. [GitHub comparison limits](https://docs.github.com/en/rest/commits/commits#compare-two-commits)

A new analysis captures its rules, quick-test policy and revision. The job’s `evidence` holds the policy, review-stage status and activity messages, GitHub Checks, and an ordered list of VM test attempts. An older job can lack this field. The independent Checks and VM workers retain their observations while the desktop is closed and resume work after restart. Reopening the same head in a later scan refreshes the Checks snapshot.

A failed Checks refresh preserves the last successful `status`, `runs` and `updatedAt`; the error and `refreshErrorAt` describe the later attempt. A first collection failure has status `error` and no successful observation time.

The Checks collection reads the latest check runs associated with the captured PR head. AXV records the name, status, conclusion and GitHub link. No runs yields `empty`. Skipped and neutral checks have their own status. API errors, inconsistent head identities and truncation at the 300-run limit are visible.

For completed GitHub Actions jobs, AXV can also record `scope` from executed job steps and `executionSha` from the primary checkout log. A matching PR merge ref yields `executionRef`. The `provenanceUrl` opens the checkout step. The provider job ID, workflow run, repository and associated head must match. GitHub's log must show the successful first checkout of the repository at its default path and its printed commit. This identifies the observed checkout. A later script can switch revisions. Custom check providers, secondary checkouts, expired logs and missing evidence leave the checkout unknown. Each collection reads at most 24 uncached jobs and the first 128 KiB of each log. Previously confirmed results can be reused for the same completed job. **Refresh checks** repeats the observation without starting Codex or a VM test. [GitHub workflow jobs API](https://docs.github.com/en/rest/actions/workflow-jobs)

A VM test resolves its repository's configured host, machine and project before submitting a persistent [Compute Task](compute.md#vm-project-tasks). The host can register per-repository selections with `AXV_REVIEW_VM_CONFIG`. Existing environment variables supply the default for unmapped repositories. The snapshot's `repositoryEnvironments` describes the selection by repository using `name` and `configured`. This status describes registration. AXV verifies the Compute binding and records the request ID for that exact binding before submission. A receipt pins the original host, project, machine, boot, task and attempt. AXV resumes observation from the recorded identity after a lost response or a change to repository configuration. The UI receives a bounded log tail, exit status, timestamps and setup errors. A completed command returning nonzero records a failed test. The exit status alone cannot attribute a regression to the PR. Provision the selected guests using the [dedicated review VM recipe](../../recipes/github-review/README.md). Direct requests outside the watch list have no test command.

A test retry checks the repository, current head and base, settings revision and latest finished attempt. Automatic retries evaluate the currently saved profiles for that comparison. A supplied profile ID overrides changed-path matching for this attempt and still requires its entry file at the head. A competing policy change before dispatch can invalidate the queued selection. Named attempts record the base SHA used for selection. A fresh review after the comparison changes can select a new test while retaining completed VM attempts on the same head. Each attempt records the selection mode, reason and chosen command when available. Earlier commands and receipts remain visible in the history. Duplicate or outdated retries return a conflict. Existing receipts stay attached to their original revision after a new head appears. For an analysis retry, a changed head requires the newer job. A changed base on the same head can be used for fresh analysis.

## Quick test recommendations

The snapshot can expose `quickTestRecommendation` for an exact reviewed comparison of a watched repository with saved tests and a configured VM. The local calculation uses the saved testing rules and prior observations. A configured test linked to a candidate with an independently completed comparison takes priority over other candidate links. Established automatic selections take priority over unrelated manual attempts. Where a specific profile cannot be established from the available information, the normal automatic selection checks the changed paths and required entry at the exact commits before the test can run. The recommendation includes `id`, `status`, `reason`, `baseSha`, `headSha`, `testName`, `latestAttempt` and the selected `testId`, `entryPath` and `command` when known.

`status: reuse` includes `reusableAttempt` and `reusableStatus` (`passed` or `failed`). AXV reuses a verified original receipt using the same comparison, saved test definition and configured VM scope. The receipt must record the actual checkout, completed Compute Task and attempt, and full original project, volume and guest binding. Failed command results additionally need a verified command exit code. An old receipt with incomplete provenance cannot be reused as exact evidence. Reuse reads local records and preserves the earlier receipt, any later attempt and all separate CI and candidate assessments. It makes no GitHub request, VM task or storage change.

`status: run` requires explicit confirmation. AXV validates the live PR comparison, then rechecks the recommendation, settings and latest attempt inside the enqueue transaction. It refuses outdated confirmations, duplicate admissions and confirmations for reusable receipts. The worker checks the confirmed base and head before submitting to the VM and uses the normal required-entry and receipt checks. The operation does not spend a Codex review start.

## Candidate comparison tests

A watched repository may configure up to eight `comparisonRuntimes`. Each entry has a stable, unique `id`, display `name` and `command` argv prefix installed on the dedicated quick-test VM. For example, `["python3", "-c"]` runs a Python assertion. If the list is empty, AXV offers the built-in `shell` runtime with `["/bin/sh", "-ec"]`. The operator confirms the assertion as one final argument. It must contain nonblank UTF-8 text of at most 8 KiB. Newlines and tabs are supported.

POST the connected `account`, `repository`, `number`, captured `baseSha` and `headSha`, current settings `revision`, occurrence `candidateId`, `runtimeId`, `assertion` and a UUID `requestId`. AXV verifies the PR against GitHub and looks up the merge base and candidate on the captured review. Retrying the same confirmation uses the same request ID. A different confirmation for an already active candidate returns a conflict. Polling may be paused. The request uses the dedicated VM and consumes no Codex review start.

AXV freezes the runtime and assertion, then submits two independently checked-out Compute Tasks. The baseline uses the reviewed diff’s merge base. The second task uses the PR head, bound to the same host, machine, boot, project and volume as the first. Each receipt retains the task and attempt identity, target SHA, observed checkout when verified, log tail and available exit codes. The guest task’s wrapper exit and the assertion’s exit code are separate fields. A missing runtime, an unverified checkout or an interrupted execution remains visible. Durable requests resume observation after a desktop restart.

A completed pair reports `both_passed`, `both_failed`, `head_only_failed` or `baseline_only_failed`. Reviewers can compare the actual output when both assertions fail. A non-comparable pair reports `inconclusive`. The run belongs to the exact candidate occurrence and keeps its existing assessment. Candidate and history snapshots include comparison summaries. Open a run’s detail endpoint for the original assertion and logs.

## Approved candidate validation

To approve a scenario, POST `{account, repository, number, baseSha, headSha, revision, candidateId, comparisonId, name, enable}`. Choose a confirmed candidate on a current reviewed comparison with a manually confirmed `head_only_failed` receipt. Both actually checked-out commits, assertion exits and original VM bindings must be verified. The approved assertion and the exact runtime are taken from that receipt. A changed runtime cannot be substituted. `enable` also opts that repository into automatic candidate validation. Settings can change `autoCandidateValidation` later. The snapshot's `comparisonScenarios` descriptors are managed by approval, scoped to the attached account and repository, and immutable through general settings. Discovery may stay paused.

For a watched repository with automatic validation enabled, AXV can offer Codex the IDs and descriptions of usable approved functional scenarios. Codex may return an optional `verificationScenarioId` with a finding. AXV validates the reference in the current repository and requires the registered file, diff side, runtime, original proof and an unambiguous claim. A different title can use that existing assertion, but the resulting receipt remains subject to human relevance review. AXV creates no suggested decision or local draft in this case. AXV uses the prior exact-title workflow when there is no reference. Unrecognized and conflicting IDs go to manual review.

The validator requires a unique match on the repository-relative path, diff side and normalized full finding title. It checks that GitHub still reports the exact target base and head and resolves the configured review VM binding. A reusable receipt must match those commits and their common ancestor, the complete approved runtime and assertion, and the current project, volume, machine, boot and guest binding. When a pending candidate lacks an eligible result, AXV schedules the existing two-leg comparison once and pins both sides to the verified binding. AXV checks the current commits before dispatching either side and keeps every original receipt. Disable the repository setting to revoke unsubmitted automatic work. Work already accepted by Compute continues observing its original task.

`autoValidation` reports `queued`, `running`, `verified`, `needs_review` or `stale`, with `reason` and any applicable scenario and comparison IDs. `reused` distinguishes reuse from a new execution. Only a verified common-ancestor pass and PR-head assertion failure produces a `suggestion.status` of `confirmed`. AXV can write a local line draft when the candidate has none. It preserves the reviewer's decision, note, linked evidence and any existing draft. Ambiguous and unmatched candidates, inconclusive results, errors and failed environment checks explain what to judge manually. A superseded comparison retains its original record and draft with stale status. No result is sent to GitHub, and automatic comparisons consume no Codex review start.

## Local candidate decisions

Each job's `candidates` array maps to its original `findings` by `index`. A candidate has an opaque occurrence `id`, a cross-version `trackId`, its review commits and text, a local `status` (`pending`, `confirmed`, or `false_positive`), a note, a positive `revision`, snapshots of its linked `evidence`, and its previous occurrences under `history`. A new review starts pending. A unique normalized title at the same path and diff side can match a single previous issue in the same account, repository and PR. Multiple matches remain separate for human review. A disappearance from the model's next report leaves the earlier judgment in history. `previousCandidates` makes earlier findings available for explicit linking even when their wording or file path changed.

For a concern that the model did not report again, `POST /api/github-review/candidate-followup` takes `{account, repository, number, baseSha, headSha, previousCandidateId}`. Use a previous candidate from that same PR. On a completed current comparison this opens a pending reviewer follow-up. Repeating it for the same track is idempotent. The job exposes these under `followups`, independently of the model's `findings` and its count. Each has `index: -1`, the original finding location and its `originId`, `originHeadSha` and `originBaseSha`. A follow-up can be confirmed on the new version, marked false positive, left pending or marked `resolved` for an issue fixed in this revision. Evidence and notes belong to the version that the reviewer evaluated. Existing verdicts and comments stay attached to their own revisions.

The owner sends `{account, repository, number, baseSha, headSha, candidateId, revision, status, note, evidenceIds, previousCandidateId}` to the candidate endpoint. Use the current candidate's revision. An empty previous ID retains its track. Select an ID from `previousCandidates` to explicitly follow an earlier occurrence. AXV refuses to join two separate findings in the same review onto the same track. Confirmed and false-positive decisions remain local. Older reviews are read-only. A stale edit, changed owner, mismatched revision or unavailable evidence returns 409. Successful saves return the current review snapshot. The note accepts 4 KiB and a candidate can carry up to 16 evidence items. Decision changes preserve the original model output and Codex quota.

`evidenceOptions` contains server-issued IDs for observed upstream CI checks and quick-test attempts for this review. CI can identify a checkout different from the PR head, and the absence of an actual checkout SHA means unknown. Evidence links retain the observation selected at save time, including its label, result, actual SHA when available and diagnostic details. A subsequent CI refresh can supersede the item in the chooser while its linked snapshot remains available.

## Local comment drafts

The owner saves a draft by sending `{account, repository, number, baseSha, headSha, candidateId, revision, body}` to the draft endpoint. `revision` is the draft's own revision, starting at zero for creation. The server derives the anchor from the verified finding on that reviewed diff. `body` accepts nonblank Markdown up to 8 KiB in UTF-8, including newlines and tabs. The save preserves the assessment, its note and linked evidence. It consumes no review starts and makes no publication request. An outdated draft, account or review revision returns `409` with `github_review_draft_conflict`.

A candidate with saved text includes `commentDraft` with `body`, `revision`, `updatedAt`, `baseSha`, `headSha`, `anchorSha`, `path`, `line`, `side` and `stale`. The `base` side anchors to the recorded merge base and the `head` side anchors to the reviewed PR head. Drafts require a recorded anchor on the reviewed diff. A reviewer follow-up refers to an earlier location and cannot create a draft at that line on the current diff. When a review is superseded, its draft remains readable at the original anchor with `stale: true`. A candidate on a new revision starts without a draft even when it shares a track with an earlier candidate.

To acknowledge a saved draft, send `{account, repository, number, baseSha, headSha, candidateId, revision, reviewed}`. Use the current positive draft revision. AXV records `commentDraft.reviewedAt` locally and preserves the comment, assessment and draft revision. Set `reviewed: false` to clear it. A newly saved edit clears the acknowledgment. Superseded drafts are read-only.

The `AXR2` review store adds its draft table and acknowledgment field through additive schema migrations. Existing settings, reviews, notes, drafts and evidence stay in the same store. AXV keeps existing notes as assessment data. A draft starts with an explicit save or a verified approved candidate validation. Automatic validation only fills an empty draft slot.
