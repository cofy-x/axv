# Desktop and Host Terminal architecture

This reference owns application extension, mounted window state, layout persistence and ordinary Host Terminal lifetimes. Read [ownership and dependencies](architecture.md#ownership-and-dependencies) first. [Design](design.md) owns visual, focus and accessibility requirements; the [desktop](api/desktop.md) and [Host Terminal](api/host-terminal.md) APIs own serialized fields and transport contracts.

## Register an application

1. Keep the `AppDefinition`, component, styles and tests under `apps/dashboard/src/features/<feature>`. Use [Preferences](../apps/dashboard/src/features/appearance/definition.ts) for a simple definition or [Terminal](../apps/dashboard/src/features/terminal/definition.ts) for resource creation and window-owned commands.
2. Import public controls and types from `@cofy-x/axv-nextstep`. The dashboard [entry point](../apps/dashboard/src/main.tsx) loads the package's `styles.css` once before [feature styles](../apps/dashboard/src/app/styles.css).
3. Add the definition to the dashboard registry. Dependencies flow from composition into the feature; features never import the registry or startup layer. Generic Nextstep behavior uses host callbacks and capabilities, never hard-coded application IDs.

`launchable` controls launcher visibility. Independently, `defaultPinned` controls whether a launchable application is pinned when creating an initial Dock; it defaults to true and does not override saved user pinning. Set it to false for utilities that should remain available through Applications and optional Dock pinning. `defaultDesktop` offers a desktop launcher unless the browser layout has an explicit visibility choice. Dashboard-supplied pure application icons carry `applicationLauncher: true`, preserving their existing IDs and launch callbacks; resource shortcuts do not. An optional `launch(desktop)` selects or creates a resource before opening its window. Use `kind: 'panel'` for non-modal inspectors and tools. Package naming follows [product identity](product.md#identity).

Nextstep reserves the desktop icon ID prefix `application:` for generated launchers keyed by application ID. Host-supplied icons use their own namespaces, preserving existing resource and launcher identities.

Tailscale is a launchable singleton utility panel. Its [feature definition](../apps/dashboard/src/features/tailscale/definition.ts) supplies the view and identity; dashboard composition supplies its system desktop icon, and the existing Applications menu, optional Dock pinning and Clip shortcuts supply launch access. Preferences also opens the same panel. The display name is **Tailscale**; its stable application ID remains `remote-access`, preserving saved windows, Dock pins and Clip shortcuts. Connection queries and local enable/disable actions belong to the feature panel, and Nextstep owns no Tailscale state or API calls. [Remote desktop usage](usage.md#remote-desktop) owns its setup and shutdown workflow.

Cloudflare is an independent launchable singleton utility with stable application ID `cloudflare` and window identity `cloudflare:main`. Its [feature definition](../apps/dashboard/src/features/cloudflare/definition.ts) offers the generated `application:cloudflare` desktop launcher by default, using the shared original `cloud-tunnel` icon, and defers the utility's heavier view code. Saved visibility choices and icon positions take precedence; there is no separate system icon or default Dock pin. The desktop launcher, Applications, Preferences and optional Dock/Clip shortcuts open the same window. Preferences groups Tailscale and Cloudflare launch actions under Remote access. Overview, Setup, Publishing and Traffic preserve their mounted drafts across tab changes; inactive content is inert and stops polling. Project preview Publish actions open this singleton with the original binding and port; another requested target cannot silently replace its draft. Setup and credential operations stay local, while authenticated owners can inspect health/traffic and manage publications. Nextstep owns no tunnel, publishing or authentication state. [Cloudflare usage](usage.md#cloudflare-desktop-access) owns the workflow, and the [transport contract](api/cloudflare.md) distinguishes local listening from public reachability.

VM Project Files can open a project-scoped Codex manager. Its window key contains only opaque host/project IDs; run windows retain the exact session/run key. The Codex and Project Files features own context, request recovery and VM navigation, while Nextstep remains unaware of project bindings or provider operations. [Codex VM work context](codex.md#vm-project-work-context) owns the integration.

## Application content loading

Feature definitions, launch functions, window keys and menus remain synchronous. Heavy views use the dashboard-owned [`deferWindow`](../apps/dashboard/src/shared/desktop/defer-window.tsx) boundary, declared once at module scope. Registry factories may rebuild metadata as filesystem or availability state changes; they must not create new component identities and remount live windows. Codex and Project Files retain lightweight dispatchers: opening the Codex manager does not require the terminal renderer, and choosing a project does not require host previews, VM file editing or task views. The Project Files launcher keeps its Host and VM panels mounted; VM file views retain their existing section and draft lifetimes.

Each view shares one in-flight module request and a successful component cache. Each window receives its current props while retaining its own state and execution identity. Pending loading shows a window-local status; a rejected request shows Retry and expandable diagnostics. Owner commands remain disabled until their handlers register. Closing a pending window removes its subscriber: a later module result may populate the module cache but cannot reopen the window or start its session.

Retry only loads content that has not mounted successfully. It does not recreate healthy windows, clear drafts, queue input or recapture project/VM/run targets. Some browser module-graph failures remain cached for the document lifetime; persistent failure guidance therefore tells users to save other work before manually reloading AXV. The boundary never reloads the desktop automatically.

Restoration keeps the existing mounted-window lifetime, including hidden windows. Once mounted, views remain mounted across workspace, shade and minimize transitions and continue receiving the existing visibility/input restrictions. Deferring unopened features does not mean hidden restored sessions are suspended or delayed until first visibility. Build preloading and measured startup/first-open costs belong to [development](development.md#dashboard-loading-and-performance).

## Installed extensions

**Application Manager** is an unpinned built-in application (`applications`) with a desktop launcher by default. It combines metadata derived from the existing built-in definitions with the installed extension catalog. Built-ins remain feature-owned React components. Dashboard [composition](../apps/dashboard/src/features/extensions/registry.ts) rejects duplicate IDs; installed package IDs are namespaced separately as `extension.<package-id>` desktop definitions. No directory precedence can override a built-in definition.

The dashboard-owned [extension adapter](../apps/dashboard/src/features/extensions/ExtensionWindow.tsx) renders installed applications inside existing Nextstep windows. Nextstep owns no extension API, installation state or business data. Packages are self-contained HTML documents with a versioned manifest; API 1 grants only private application storage. Its optional icon selects controlled shared artwork and falls back to a document. New extensions have no default desktop launcher or Dock pin. Installation and management are explicit, local actions. The [Extensions API](api/extensions.md) owns package validation, content policy, session authorization, limits and remote access.

An extension document has an opaque sandbox origin, with scripts enabled but no same-origin access. Content responses enforce their own sandbox even when opened directly; the desktop also restricts frame navigation to its own origin. Documents receive neither workstation credentials nor backend session identifiers. No document, project, terminal, agent or VM capability is exposed. External assets, modules, workers and network access are not part of API 1.

The host captures the iframe on its initial load and transfers a dedicated `MessagePort` through a nonce handshake. A timeout, navigation, installation change or window destruction closes that port and invalidates its client generation. The host retains the exact app/version/session; the backend revalidates its installation generation on every storage operation. Non-catalog API operations carry the captured extension-store identity, and content addresses include that identity, so replacing the store cannot redirect an older window's actions. The [browser broker contract](api/extensions.md#browser-broker) owns the message shapes, supported methods and failures. It exposes private data reads/writes, local draft retention and focus for the originating window, without a general desktop or HTTP interface.

The [example SDK](../examples/extensions/sdk.js) handles the port and request timeouts; [Checklist](../examples/extensions/checklist) demonstrates explicit saves, later typing, conflicts and recovery. It checks the complete serialized document before accepting an edit and rejects over-limit changes while retaining its last accepted text. Its [package adapter](../apps/dashboard/src/features/extensions/sample.ts) inlines that SDK into one HTML document. Developers can download the resulting JSON from Application Manager and install a modified package after review.

The [runtime](../apps/dashboard/src/features/extensions/runtime.ts) owns exact save snapshots, close guards and browser recovery. Saved content and later typing remain distinct. Failures retain dirty data; a late response from an old connection cannot clear or replace a newer draft. Recovery uses the extension store identity, browser client and an independent [editor session claim](../apps/dashboard/src/shared/drafts/session.ts), so live tabs cannot overwrite one another's recovery records. A copied recovery record is read as a source and written under the new identity; clearing the copy does not delete its source. Restore and discard require a choice and retain the original expected revision. Recovery is local to that browser origin and is not a substitute for a successful server save.

A rejected draft also blocks saving, closing, reload and installation changes until a valid draft update or explicit discard resolves it. The host keeps the rejected payload in memory for JSON export when possible, without writing it to recovery or the server. This protection does not make the rejected content recoverable after browser navigation or reload.

Catalog reads refresh while the desktop is subscribed and on browser focus. A failed read retains the last catalog with a visible error. Upgrading, disabling or uninstalling does not silently reload an existing window: the old port is suspended and its iframe disposed, while the trusted host retains the window and its draft. The new installation is loaded only by an explicit reload. Local management checks live drafts in this browser before changing the installation; other clients retain their own recovery and encounter a revoked session. Uninstalling keeps saved data, and deleting that data is a separate confirmed operation. Visible workflows belong to [usage](usage.md#applications-and-extensions).

Composition retains identity, title and icon metadata for applications seen during this page's lifetime even when a replacement store omits them, keeping their trusted window hosts mounted for draft export or explicit close; the management directory still shows only the current catalog.

## Window identity and visibility

`windowKey(params)` defines identity for a new window within an application. Preferences uses a singleton key and Files an anchor directory ID. [Text Editor](../apps/dashboard/src/features/notes/definition.ts) uses a file ID for ordinary opens and a distinct draft ID for recovered drafts or **New View of Document**. Paths and display names are not document identities. Restored windows retain their validated saved IDs, including while an application definition is missing; adding the definition later does not recompute or replace those identities. Opening the same application and complete parameters restores its existing window before creating a new identity, switching workspaces when needed. File browser navigation updates view state without changing the anchor; using **Open** on a directory opens or activates the window identified by that directory.

Use `DesktopAPI` for desktop actions and `beforeClose(windowId, guard)` for an asynchronous close guard with cleanup. Feature commands register against a live window ID in the dashboard's typed command registry and unregister on close.

All windows retain stable identity in the same React tree. Folded, minimized and off-workspace content stays mounted, preserving drafts, selection and scrolling, but cannot receive pointer or keyboard input. Features use `AppWindowProps.interactive` to suspend input and focus behavior without disposing their content. Modal dialogs constrain focus and block conflicting workspace actions; Inspector and fixed menus remain non-modal.

## Menus and workspaces

`MenuGroup` and `MenuItem` describe nested items, checked/disabled state, shortcuts and actions. Optional item descriptions appear below their names in both popup and fixed menus. Context menus can request a wide layout and align their end edge to the supplied point; placement and scrolling remain bounded by the visual viewport, including a reduced viewport height. A transient content menu may bind an owner window; losing that window’s active, visible content cancels the menu and rejects its actions. Fixed menus retain their independent owner-bound lifetime. Keyboard navigation scrolls the active item into view. Fixed menus persist descriptors containing their kind, menu group and optional owner window ID, never callback closures. Actions resolve against the live owner at execution time. Changing the active window cannot retarget a fixed menu; closing its owner invalidates it.

Stable workspace IDs have editable names. Each workspace owns Clip shortcuts, stacking order and an active window. A window belongs to one home workspace and may be sticky across workspaces. Dock state represents applications and stores pinning and order; live windows supply running state and the window chooser. Minimized windows have separate restore icons.

Dock touch and pen gestures use native scrolling along the Dock's layout axis; only mouse pointers enter custom drag ordering. The tiles, clock and surrounding controls permit the same native pan direction. Visible ordering commands remain available to touch and keyboard users. A cancelled drag clears its feedback without persisting an order or suppressing a later activation.

## Geometry and desktop icons

Moving, resizing, maximizing and narrow-screen fitting use one computed work area. The miniwindow strip reserves space only when the current workspace has visible minimized windows, including sticky windows. The Dock reserves its own space. Workspace or shelf changes adjust displayed bounds without overwriting normal geometry or `restoreBounds`.

The visual viewport also selects a short-height shell layout, including when an on-screen keyboard reduces the available height. Clip becomes a single workspace-menu button; its menu retains workspace switching and all shortcuts. Application menus occupy one horizontally scrolling row beside it. Short landscape screens with sufficient width use the full-size, vertically scrolling side Dock; narrower screens retain the bottom Dock and full application width. Miniwindow restore icons keep their separate shelf. [`desktopLayoutMode`](../packages/nextstep/src/model.ts) supplies the same presentation conditions to the shell and work-area geometry; resizing or rotating does not rewrite saved window, Clip or icon positions.

Desktop icons use the same shell bounds. Default placement and arrangement fill columns from the right; drag limits reserve the menu, Dock and visible miniwindow strip. Compact bounds reserve the top menu/Clip and the current Dock edge. Wide and compact layouts retain independent icon positions. Temporary fitting moves displaced icons into free cells without persisting those adjustments. A full grid adds rows reachable through the desktop canvas's own scroll area.

Application Manager uses `DesktopAPI.isApplicationOnDesktop(appId)` and `showDesktopApplication(appId, shown)` for its **Show on desktop** controls. Visibility belongs to the browser layout, independently of installation permissions, enable state and Dock pins. Hiding a launcher keeps its saved wide and compact positions. Choices for missing or uninstalled applications remain stored without launching them; an available definition can restore the launcher later. Workspace, Documents, Recycler, virtual files and individual VM resource icons retain their own visibility rules.

Dashboard composition combines filesystem entries, application launchers and feature-owned VM projections. VM icon IDs and Inspector targets bind the host and machine IDs, while names remain labels. Derived VM icons use layout positions keyed by that identity without copying machine records into desktop storage. A confirmed inventory removes deleted targets; connection failures retain the last complete inventory as unavailable. Inventory snapshots must belong to one verified host connection generation.

Generic `DesktopIcon` status text and tone provide resource state without application-specific branches in Nextstep. Its `trashable` capability is opt-in: only eligible virtual filesystem entries route to Recycler or keyboard deletion. System and VM selections have their own dashboard menu actions and cannot fall through to file operations. Opening a bound VM restores its existing Inspector across workspaces; a missing or mismatched target remains unavailable rather than rebinding the window.

## Persistent layout and recovery

`DesktopLayout` stores desktop presentation and resource references. Serializable `DesktopWindow.viewState` holds small view settings such as a column path or pinned Inspector target. Layouts contain no document drafts, terminal instances, scrollback or process state. The [desktop API](api/desktop.md) owns the serialized format and version.

`updateWindowState` accepts a patch or a pure function of the latest queued view state. Reconciliation uses the functional form so a delayed effect cannot overwrite newer navigation with an older render's snapshot. File browsers repair paths after metadata changes, preserving the current folder by ID after moves or recovering its closest surviving ancestor after deletion. Selection and scrolling do not rewrite the location.

The dashboard saves layouts with a stable browser client ID through a serialized queue and short debounce. Pending changes coalesce before writing; pointer previews do not write every frame. A failed request cannot replace a newer pending layout. Failures remain visible and retryable. Unknown layout versions retain the server record and suspend writes until explicit reset. Invalid fields and missing references are repaired independently of virtual documents; viewport fitting preserves usable desktop geometry.

Missing application definitions are retained as unavailable windows, Dock entries and Clip shortcuts, with their original IDs, parameters, view state and menu owners. They are not invalid layout data. A generic placeholder executes no application code, and a later definition restores rendering under the same window key. `AppDefinition.unavailable` offers the same presentation for a registered but unavailable application. Disabling an installed extension instead suspends its feature-owned runtime, preserving its local draft. Users may close an unavailable window or remove a shortcut explicitly; catalog loading or failure never removes them implicitly.

Preferences are shared by the local user; layouts are isolated by browser client ID. Tabs sharing that identity share the saved layout, so the last successful writer wins. Recovery draft IDs remain distinct. The [storage reference](storage.md) owns document revisions and browser recovery; layout repair never resets files.

## Terminal sessions

`features/terminal` owns one xterm.js instance, FitAddon, WebSocket and resize observer per window. Its controller owns startup, byte queues, sizing and explicit restart after exit or failure. Terminal commands use the window-owned registry, so a fixed menu continues to address its original terminal.

Folding, minimizing or switching workspaces preserves the emulator and shell. `interactive` suspends input and blurs the emulator without disconnecting it; hidden content cannot consume keys or take focus from menus and dialogs. Closing a live window uses the shared confirmation dialog, then disposes the emulator and connection. Connection loss ends the shell; restoring a window after reload or choosing New Session creates a fresh shell rather than reconnecting a process.

The Go service owns `terminal.Manager` independently of storage. It validates local access and Origin, enforces capacity, and bridges WebSocket bytes to a host shell. Platform adapters in the server terminal package own PTY creation, resizing, exit detection and process cleanup; dependency versions belong to the [Go module](../apps/server/go.mod).

The shared [`nativepty`](../apps/server/internal/nativepty) adapter creates pollable PTY masters for Host Terminal, Codex attachments and Guest Terminal. It preserves nonblocking I/O through `SyscallConn`; each feature retains its own process waiting, termination and detach rules.

On macOS/Linux, the process waiter retains the exit code, signal, duration and requested-close state in [service diagnostics](startup.md#configuration-and-storage), without terminal streams or environment values. It publishes process completion before logging so diagnostics cannot delay session cleanup.

Service shutdown closes ordinary Terminal connections and reaps their shells explicitly: `http.Server.Shutdown` alone does not close upgraded WebSockets. [Codex attachments](codex.md#terminal-attachments) have a separate lifetime. Framing and same-origin checks belong to the [Host Terminal API](api/host-terminal.md); the development proxy must preserve browser Host and Origin.

### Clipboard input

Host Terminal, Guest Terminal and Codex share a dashboard-owned [paste flow](../apps/dashboard/src/shared/terminal/use-terminal-paste.tsx) and native editable fallback. The [operation controller](../apps/dashboard/src/shared/terminal/terminal-paste.ts) owns request invalidation and local input acceptance. Clipboard reads begin directly in the user action; read failures and terminal input failures have separate feedback. The fallback uses shared controls in the desktop dialog, but terminal identity and lifecycle remain feature-owned. [Terminal clipboard](usage.md#terminal-clipboard) describes the visible workflow and line-break behavior.

Each paste operation captures its emulator, connection and input generation. Leaving the connected state or disposing/replacing the connection invalidates pending reads and editable fallbacks, even if that controller later reconnects. A stale completion cannot open a fallback or send to later work. The fallback retains text after input rejection and never retries automatically. Input still passes through xterm's paste handling; accepted input means queued locally, not acknowledged by the shell. Explicit fixed-menu commands retain their original window owner, while dialogs and hidden terminals preserve their existing focus boundaries.

### Project terminals

`openTerminalWindow(desktop, projectPath?)` accepts an optional real host directory. The initial path is serializable window metadata. The server resolves symlinks, checks directory access and assigns the canonical path through the process working-directory API. It never constructs a shell `cd` command or falls back to home after validation fails. HOME remains the service user's home.

New Session and restored windows start fresh shells in the selected initial directory, not a later `cd` location. Host paths remain separate from virtual document IDs. The generic desktop package supplies frames and controls; shell policy, terminal dependencies and host connections belong to the feature and server. See the [Host Terminal API](api/host-terminal.md) for protocol details.
