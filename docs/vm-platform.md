# VM architecture

AXV runs VMs on the machine where it is deployed, for one trusted local user. The host service manages that machine's local virtualization provider; the interface does not select a separate host. Machine, project-volume, guest terminal and desktop-window identities remain separate. The [architecture overview](architecture.md#vm-operation) shows request dispatch; this guide covers recovery, provider boundaries and guest lifetimes. See [project status](../README.md#project-status) for support and [Using AXV](usage.md#virtual-machines) for user actions.

## Ownership

The [`compute`](../apps/server/internal/compute) root package supplies shared records, configuration, validation, lifecycle policy and provider driver contracts. It also owns shared guest transport and image inspection. [`compute/control`](../apps/server/internal/compute/control) owns the controller, SQLite store, operation queue, recovery and embedded migrations. Concrete provider drivers depend on the shared contracts; the controller calls those driver interfaces, and [`compute/host`](../apps/server/internal/compute/host) composes the implementations with the private host API.

The desktop [`compute/gateway`](../apps/server/internal/compute/gateway) and [`compute/client`](../apps/server/internal/compute/client) share private-socket identity, protocol and configuration verification through [`compute/internal/hostconn`](../apps/server/internal/compute/internal/hostconn). The CLI and application startup use the client without maintaining separate HTTP implementations. Runtime identity checks do not probe providers; provider availability is an explicit information query. The nested `internal` boundary limits connection implementation access to compute packages. The host [`compute/httpapi`](../apps/server/internal/compute/httpapi) adapter invokes the controller; the gateway and client use the host's transport contracts independently of its store.

[`compute/prepare`](../apps/server/internal/compute/prepare) owns preparation tasks, configuration publication, failure classification and retry eligibility. It shares profile storage through [`profile`](../apps/server/internal/profile), with activation supplied by [`app`](../apps/server/internal/app) through the preparation engine's callback contract. Its [`httpapi`](../apps/server/internal/compute/prepare/httpapi) subpackage owns request decoding and maps domain failures to HTTP responses through a consumer-defined service interface. [`compute/artifacts`](../apps/server/internal/compute/artifacts) owns the reviewed release catalog; [`compute/ubuntusources`](../apps/server/internal/compute/ubuntusources) owns guest package-source policy. These VM-specific packages share the compute namespace while preparation and controller state retain separate lifecycles. The generic download cache remains in [`artifactcache`](../apps/server/internal/artifactcache).

The [`guest`](../apps/server/internal/guest) package owns the VM execution service. Its [`protocol`](../apps/server/internal/guest/protocol), [`image`](../apps/server/internal/guest/image) and [`sshkey`](../apps/server/internal/guest/sshkey) subpackages are shared with host callers and image tools. Guest-only SSH and network handlers live in [`guest/internal/access`](../apps/server/internal/guest/internal/access), whose nested `internal` boundary prevents host packages from importing that implementation. The shared [`sshstream`](../apps/server/internal/sshstream) transport owns framing and half-close behavior independently of guest service state.

The host owns VM, volume and image records, capacity admission and reconciliation. Desktop and CLI clients share its validation, creation defaults and durable operation model. The desktop forwards verified requests; the VM CLI connects directly without initializing desktop state. `compute.sqlite` is separate from `desktop.sqlite`; its feature-owned [`0001_initial.sql`](../apps/server/internal/compute/control/migrations/0001_initial.sql) uses the **AXC1** (`0x41584331`) file-format marker. Preparation embeds its own [`0001_initial.sql`](../apps/server/internal/compute/prepare/migrations/0001_initial.sql) with **AXP1** (`0x41585031`). Each independent migration sequence currently starts at version **1**, executed by the shared [transactional runner](storage.md#migration-runner). File type/baseline identity is separate from migration order: old unmarked compute/preparation databases, another database type, future versions and nonempty unversioned files are rejected without reset. The host identity is initialized transactionally once and cannot acquire a second row. Preparation has a profile-scoped database because it must work before a compute database exists and independently of desktop `DATA_DIR`. Exclusive data-directory and socket locks prevent competing controllers.

Desktop and compute services communicate through a Unix socket on the deployment machine. The internal `compute.mode: external` setting means the local compute service is independently supervised, as required for privileged Linux hosting; it does not select a remote machine. [Startup](startup.md#configuration-and-storage) owns service-mode configuration.

The [compute gateway](api/compute.md) enforces local access; host-socket permissions let group members control all managed machines and guest data, without per-machine authorization. Desktop/controller shutdown preserves VM processes and disks. Restart resumes interrupted work and observation; stopped VMs require explicit start. [Startup](startup.md) owns configuration and service supervision.

## Environment preparation

The runtime coordinator starts after desktop readiness and owns environment detection and service activation. Missing dependencies or unavailable compute do not block the desktop. Checks publish a cached snapshot; viewing status does not install dependencies or repeatedly probe providers. An already configured managed service is verified for reuse or started using the current launcher's ownership rules. Independently supervised Linux services are only inspected and connected.

The shared preparation engine resolves a concrete plan before execution. The plan fixes input paths, budgets, artifact versions and digests; Web and CLI use the same validation. Confirmed tasks persist request identity, steps, transfer progress and configuration commit intent in `AXV_HOME/preparation/preparation.sqlite`. One task may run per profile. Browser disconnects do not affect execution, while process interruption leaves a task that can be explicitly retried. The [Compute API](api/compute.md) owns plan and task contracts.

The shared [`artifactcache`](../apps/server/internal/artifactcache) infrastructure owns immutable public downloads, cache partials and per-digest cross-process locks independently of any profile. It hashes complete contents under the lock before reuse, then makes independent profile copies. Cancellation preserves only its own partial progress; cache maintenance skips active downloads, imports and copies. Profile loss does not discard a resumable shared transfer. Cache paths and maintenance belong to [startup](startup.md#shared-download-cache).

Image-source selection follows the [setup policy](startup.md#first-time-macos-setup). Official AXV, custom bundle and Ubuntu-base paths share subsequent checksum, registration and provider setup. Private user images do not enter the shared cache. Confirmed plans freeze architecture, artifact metadata and the cache location; catalog changes cannot retarget retries.

Extraction uses task-owned staging and complete content verification before publication. A private Lima installation preserves the official release layout and licenses. Matching installed runtimes and verified cached assets are reused. The engine does not install global tools or execute arbitrary browser-supplied commands. A failed or cancelled task never authorizes deleting existing VM storage.

Configuration publication records its intent before writing the host configuration and updating the profile. Recovery compares the saved intent with actual files so its own committed work can be recognized without accepting unrelated content. The profile command lock covers only short commit/ownership sections; network work and service-readiness waits occur outside it. Existing provider pins and storage ownership remain authoritative. Lima storage is ultimately owned by the compute database's host identity, not by a preparation task.

Activation verifies service identity, protocol, effective configuration, controller recovery, provider availability and usable images before publishing readiness. The gateway captures one binding generation for each request and attachment; an existing Guest Terminal is never silently redirected. Foreground cleanup owns only its child. Native daemon records track the independent host job across desktop restarts and later stop commands.

## State and operations

A transaction records intent, reservations, dependency locks and a durable operation before provider I/O. Dependencies include images, attached machines and copy-source volumes. Request fingerprints bind retries to that intent. Revisions protect requested changes; observations and guest readiness do not increment them. Worker and observation concurrency are bounded by host configuration. The journal retains execution inputs for recovery while public operation responses omit them. The [Compute API](api/compute.md#actions-and-durable-operations) owns request-ID and retry obligations.

Machine names share one host-wide namespace across current and pending specifications. Transactions reserve both sides of a pending rename, including after failure, and release the old name only on completion. A deleted record releases its name only when deletion completes. The [name contract](api/compute.md#machine-creation-and-configuration) keeps CLI resolution deterministic without making names durable identities; operations and connections retain the stable machine ID.

Restart requeues interrupted running operations under the exclusive host lock. Replay resumes the recorded phase against inspected, owned resources. Finalization is idempotent; failed result commits retry persistence without repeating provider work. Cancellation leaves running work for recovery.

Failed inspection retains reservations and pending protections. An uncertain observation can accompany a failed operation; it is never proof of a stopped VM or permission to replace missing prepared disks. Pending growth retains the larger reservation and blocks start; uncertain attachment protects both volume and destination VM from deletion until retried.

### Capacity and leases

CPU/memory admission precedes start; disk budgets include stopped roots, detached volumes and managed images. These are logical limits, not measured usage or physical free-space guarantees.

Task lease expiry queues deletion even during active work; enforcement needs a running controller and may wait for conflicting operations. Project-volume retention is independent of expiry. Root disks are disposable; retaining or copying a project volume does not back up a whole VM. The [Compute API](api/compute.md) defines development/task policies and their fields.

## Storage and providers

Each VM has a root disk and at most one attached project volume; starting requires a ready volume. Volume operations keep machine specifications and attachment ownership consistent, including when a provider result is uncertain. Provider capabilities determine available actions; the [Compute API](api/compute.md#volumes) owns compatibility checks, stopped-state requirements and allowed growth.

Images are immutable catalog records. Lima publishes native cloud images only after SHA-256 and self-contained raw/qcow2 validation of HTTPS downloads or uploads. Referenced images cannot be deleted; imports do not alter existing VMs. Administrator image files remain administrator-owned. Provider paths, binaries, versions and ownership are pinned to the data directory, never used to adopt or recreate resources. Cleanup touches only verified AXV-owned resources.

- **Lima/VZ on macOS:** Uses supported `limactl` commands and JSON inspection with private `LIMA_HOME`, without internal-state edits or personal-instance adoption. It disables host mounts, containerd, SSH-agent forwarding and automatic TCP/UDP forwarding on all guest interfaces. Guarded first-use project-disk initialization never reformats existing/ambiguous signatures; validation accepts raw and self-contained qcow2 before VZ's first-boot conversion.
- **Firecracker/KVM on Linux:** Uses an independently administered privileged compute service on the AXV deployment machine, with jailer, cgroup v2 and owned TAP/nftables state. The desktop connects through its local Unix socket. [Linux setup](startup.md#linux-privilege-boundary) owns administrator provisioning, and [`images/guest`](../images/guest) defines rootfs construction and project-disk preparation. Per-machine private networks allow public IPv4 egress while blocking host, private/link-local, other guest networks and IPv6. AXV neither changes global sysctls nor flushes unrelated firewall rules. These guest-privilege and network boundaries differ from Lima's; they do not promise identical isolation.

Firecracker keeps durable root, project, seed and kernel files in the owned machine directory. Each confirmed stopped-to-running transition rebuilds only its separately owned runtime jail and links those files into it, removing stale jailer devices, PID files and sockets without replacing disk contents. Executable symlinks resolve before pinning and choosing the jail path. VMs join preconfigured resource-control leaves under the explicitly delegated `cgroupParent`; jailer does not enable controllers in global ancestors. Missing metadata with remaining disks/runtime resources cannot authorize a new identity or token. Missing durable files, ownership mismatches and unknown previous layouts fail visibly instead of being reconstructed or adopted.

Project disks in both the durable directory and runtime jail must link to the same verified global volume. Reusing a volume with missing storage cannot create an empty replacement. Deleting a retained-volume VM verifies that the global volume preserves its project data before removing local links; an initial preparation that never created a project disk can still be deleted.

### Host firewall integration

Firecracker creates one owned nftables `inet` table per AXV host identity. Its input and forward filters run at priority `-5`, affect that identity's TAP interfaces and reject guest traffic to the host, private/link-local and other special-use IPv4 destinations, other guests and IPv6. Egress and configured DNS resolvers share the [public IPv4 policy](../apps/server/internal/compute/network_policy.go), including its globally reachable anycast exceptions. An owned set binds each TAP to its exact guest IPv4 address, preventing a guest from impersonating another guest or an external source; an unregistered TAP cannot forward packets. Masquerading applies only to traffic entering those TAPs. The table name and TAP prefix are `axv` followed by the final six characters of the host ID, with three-digit machine slots appended to TAP names. Administrator firewall rules should match this exact prefix, guest subnet and intended uplink, rather than every `axv*` interface.

The administrator must enable IPv4 forwarding and permit the intended guest egress in every other applicable host firewall. An nftables `accept` verdict ends the current base chain; [later base chains can still drop the packet](https://wiki.nftables.org/wiki-nftables/index.php/Configuring_chains#Base_chain_priority). Changing AXV's chain priority cannot bypass another firewall's denial. AXV does not edit another service's chains, change their policies or claim that provider availability verifies Internet access.

For a Docker host using its iptables backend, Docker documents [explicit forwarding rules in `DOCKER-USER`](https://docs.docker.com/engine/network/firewall-iptables/#allow-forwarding-between-host-interfaces). Authorize outbound packets only from the exact AXV TAP prefix and guest subnet to the chosen uplink, with connection state `new,established,related`; authorize return packets only from that uplink to the same TAP prefix and subnet, with state `established,related`. AXV's earlier isolation drops continue to apply. Other firewall managers require their own administrator-managed integration; Docker's [nftables backend](https://docs.docker.com/engine/network/firewall-nftables/) has a different contract. Preserve unrelated rules and record how to remove only the added rules. Verify public guest egress and host/private/guest isolation after firewall changes or restarts.

The provider records network initialization intent, subnet, a nonce and the exact static-rule fingerprint in `firecracker/network.json` before installing its table, then marks the baseline active. Interrupted initialization can resume only its exact recorded rules. Active rules are verified before reuse; missing dynamic source bindings can be restored for verified owned TAPs, but a missing active table or changed static rules fail visibly. TAP creation establishes ownership before making the device persistent, so an interrupted initial setup leaves no unmarked persistent interface. Older unversioned or unknown baselines, a changed subnet and an existing table without its baseline marker are rejected. Resetting that state requires explicitly stopping affected VMs and removing only their verified AXV-owned network resources and marker; AXV does not silently adopt or rewrite unknown rules.

## Image and capability contract

A bundle has `version`, immutable `id`/`name`, `provider`, `arch`, a rootfs filename and SHA-256, plus optional `guest` metadata. A missing guest contract represents an ordinary Linux image. The contract declares `imageVersion`, `protocolVersion` and capabilities (`exec`, `terminals`, `ssh`, `network`); optional `binarySHA256` checks that image's own preinstalled executable, never the current application build. Current compatibility requires image contract **1** and guest protocol **3**. Rootfs/kernel digests continue to protect artifact integrity independently of compatibility.

Provider lifecycle and guest readiness are separate. Create/start/restart succeed when the provider confirms the intended running state even if guest initialization, protocol or readiness fails. Ordinary Linux images retain basic lifecycle operations. The controller publishes `guestState`, diagnostic `guestReason`, `ready` and the intersection of declared and runtime-confirmed capabilities; it never grants a capability from metadata alone. Guest-dependent backend/CLI requests recheck this handshake, and desktop terminal actions require the confirmed `terminals` capability. Incompatible or absent guest software cannot disable basic VM management.

## Guest execution

The Linux guest service runs as `axv` (UID 1000). Per-machine tokens authenticate host requests over Firecracker vsock or Lima's SSH/private Unix-socket transport. Readiness verifies protocol, machine identity and a writable project filesystem distinct from root. Commands have bounded concurrency, duration and output; project-relative starting directories do not sandbox ordinary guest processes. The [Guest API](api/guest.md) owns transport and limits.

Lima's relay connection owns its output reader independently of process reaping, so buffered guest responses remain readable after the relay exits. Closing the connection releases its pipes and reaps only that relay.

Graceful shutdown uses the verified installed image's provider: Firecracker requests a guest reboot, which exits its VMM, while Lima requests poweroff. Firecracker's image grants only the corresponding reboot command through sudo. A guest halt alone can leave Firecracker running, so it is not used as graceful completion. The host observes process exit and retains its bounded force-stop fallback for unavailable or unresponsive guest services.

Guest Terminal binds the exact machine, Linux boot ID and terminal ID. Reattach replays a bounded output tail to that identity; it never creates another shell.

Closing a window or disconnecting detaches without ending its shell. End Session terminates the terminal's process group. Records last only for the guest-service lifetime: service restart loses them even with an unchanged Linux boot ID. VM shutdown ends live sessions; neither browser nor controller reconstructs them. Deliberately daemonized processes may outlive a terminal as VM workloads.

### Guest SSH and network access

A dedicated OpenSSH service listens only on guest loopback at `127.0.0.1:22222`. It accepts the `axv` account using public keys and supplies standard shell/exec, PTY, SFTP and TCP forwarding. Remote-forward listeners stay on guest loopback; root/password login, agent forwarding, X11 and tunnels are disabled. This service does not grant new sudo privileges or alter Lima's management SSH service. Guest commands retain the account's normal filesystem permissions rather than a project sandbox.

Root-owned `/etc/ssh/axv` contains the machine's persistent Ed25519 host key, dedicated server configuration and ownership markers. Missing initialized keys and mismatched ownership fail rather than generating a new identity. The guest service updates only its dedicated client registry under `/var/lib/axv-ssh/clients`, leaving unrelated authorized-key files intact. The local CLI owns its profile key and known-hosts pins; [startup](startup.md#ssh-file-transfer-and-forwarding) owns those operator details.

The CLI carries standard SSH bytes through an HTTP upgrade over the verified private host socket, then the existing authenticated guest transport to loopback sshd. Explicit EOF framing preserves half-closes; no public TCP listener, browser relay or guest-IP reachability is required. Host, machine and boot checks prevent reconnecting an old request to replacement work. SSH has ordinary connection-bound sessions and does not acquire Guest Terminal replay or recovery semantics. The [Guest API](api/guest.md#ssh-access) owns route, framing and key limits.

Both providers use [prebuilt image services](../images/guest/README.md). Start does not fetch packages, inject binaries or upgrade images. Lima initializes only per-machine configuration and SSH identity using preinstalled helpers; Firecracker uses its seed/initializer. Missing dependencies affect guest enhancements with a concrete diagnosis and an explicit image rebuild/import path. Existing compatible images remain usable across application builds. Updating guest software requires an explicit image build/update and new immutable image identity.

An explicit Lima start repairs a boot-added account lock only when the stored value is AXV's exact `!*NP*` marker, restoring `*NP*` after verifying initialized machine ownership. It preserves other account values and, when the guest and SSH services are healthy, keeps both services and active sessions running.

Network inspection reports current guest interfaces and boot identity, with provider-specific reachability from the deployment host. It does not change networking or treat a guest address as proof of host access. The private SSH transport works independently of those reported addresses.

## Desktop integration

The `machines` feature owns forms, storage controls, Inspector and Guest Terminal. All VM windows subscribe to one browser-local inventory store: inventory polls every five seconds, while environment/provider probes run initially, on explicit refresh and during connection recovery. The last subscriber stops polling. Failed refreshes retain the last successful inventory with an offline indication. Shared lifecycle checks account for machine and volume operation locks, pending configuration and guest readiness. Polling preserves edited drafts, revision conflicts and lifecycle errors. Ambiguous mutation failures retain the original target, payload, revision and request identity for retry; an accepted configuration snapshot does not discard later typing. Layout stores IDs/view state, never project contents or credentials; generic Nextstep has no VM/provider knowledge. Selecting a VM does not redirect ephemeral Host Terminal, Host Codex or SQLite virtual-document APIs to that guest.

The [mdlayher/vsock](https://github.com/mdlayher/vsock) transport is MIT-licensed. Guest images retain upstream licenses in `/usr/share/doc`; image inputs and generated disks are not vendored.

## Mirror ownership

`compute/artifacts` applies digest-keyed download mirrors before plan confirmation; `artifactcache` owns content verification and source-bound partials. `compute/ubuntusources` separately owns guest APT configuration, shared by explicit image builds and Lima maintenance. Neither boundary changes image compatibility.

The durable `package-source` action uses the controller's revision, replay and resource locks. Lima verifies machine ownership and invokes its management transport independently of AXV guest health. The source script uses a process-held lock and idempotent publication; it never invokes a package manager. VM Start never calls it. [Startup](startup.md#download-mirrors-and-guest-package-sources) owns mirror selection, supported source layouts and backup/recovery behavior; [image recipes](../images/guest/README.md#package-source-selection) own build-time dependency installation, and the [Compute API](api/compute.md#package-source-maintenance) owns request and failure contracts.
